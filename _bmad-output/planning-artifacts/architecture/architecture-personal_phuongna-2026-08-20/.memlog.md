- (decision) Paradigm + stack chosen (coaching, 3 alternatives shown): Next.js full-stack monolith - single codebase serves both UI (React Server/Client Components) and backend (API/Server Actions) in one process, backed by a local SQLite file via Prisma ORM. Chosen over (a) pure client-side SPA with in-browser WASM SQLite (rejected: newer/less common persistence pattern, higher risk for an AI-agent build with a non-technical user) and (b) React+Express+raw-SQL split (rejected: more moving parts to keep in sync, hand-written SQL more error-prone for an AI agent than an ORM). Deciding factor: user has no web dev experience and will rely on an AI coding agent to build - Next.js+Prisma+SQLite is the most mainstream, best-documented current pairing, minimizing agent drift.
- (version) Next.js 16.3.x (LTS, current stable Aug 2026, verified via web search) pinned. Prisma ORM 7.10.x pinned (not the newer Prisma 8 released 2026-08-02 - too recent for reliable AI-agent training-data coverage; 7.x is stable and well-documented with SQLite via the better-sqlite3 adapter).
- (decision) Module boundaries: 4 independent feature modules (schedule, expense, meal, learning), each owns its own Prisma models/tables exclusively; no module may read or write another module's tables directly. Generalizes PRD's 'Thuc don khong lien ket Chi tieu' non-goal into a system-wide rule preventing future accidental coupling between any of the 4 modules.
- (decision) [ADOPTED] Historical immutability: mutable 'current config' (Routine Template, this-month's-budget-in-progress, current Roadmap position) is modeled separately from generated historical/snapshot rows (past DailySchedule rows, past Transactions, completed Milestone records). Editing config never updates/rewrites past snapshot rows - this directly encodes the append-only behavior already established in PRD FR-1/FR-2/FR-5/FR-13 and EXPERIENCE.md's 'append-only edit' component pattern.
- (decision) State mutation pattern: Next.js Server Actions are the sole mutation path from UI to database - no separate REST/API route layer for CRUD. Prevents two parallel mutation surfaces (Server Actions vs API routes) drifting apart in validation logic.
- (decision) File storage: uploaded photos (Mon an, Nguyen lieu) are stored as files on local disk under a dedicated app-data directory; the SQLite DB stores only the relative file path, never blob data - keeps the DB file small/inspectable and backups simple.
- (decision) [ADOPTED] No auth/single-tenant: no User/session/auth model anywhere in the schema - every table is implicitly scoped to the one local user, per PRD Non-Goals (no login, no multi-user).
- (decision) [ADOPTED] Operational envelope: single local environment only - app runs via 'npm run dev' on the user's own machine, SQLite file and uploaded photos live in a local app-data directory outside the git repo (gitignored), no hosting, no CI/CD pipeline, no staging/prod split. Per PRD Non-Goals (desktop-only, single machine, no sync).
